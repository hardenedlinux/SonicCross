# SonicCross

SonicCross is a pure Guile 3.0 / Scheme reimplementation of PyTorch's
`torchgen` — the code generator that turns `native_functions.yaml` and
`tags.yaml` into the C++ operator registration, dispatch, and declaration
sources that ship in libtorch. It is a *semantic-equivalent* compiler: given
the same frozen PyTorch inputs it produces C++ artifacts that are byte-identical
to upstream torchgen's output.

## Status

**v0 is complete.** The full generation closure — the 75-entry artifact manifest
plus emitter groups G1–G20 — is byte-identical against the frozen baseline, and
the `guild torchgen` production entry point is wired end-to-end: it reads
`native_functions.yaml` through the libyaml FFI, renders the closure, and writes
the C++ artifacts and `--output-dependencies` depfiles to disk, with **no Python
dependency anywhere** in the path.

**Per-operator headers are also generated.** Beyond the frozen v0 aggregate
closure, SonicCross natively emits the `ATen/ops/*.h` per-operator header set
and the per-operator `Register{key}.cpp` sources under the opt-in
`--per-operator-headers` flag — the same split upstream torchgen produces for
CMake per-operator builds. This is byte-identical to frozen torchgen
(`gen_per_operator_headers`), so the 237 native-dispatch translation units can
drop the aggregate `NativeFunctions.h`/`Functions.h` dependency and include only
the operator headers they need. The frozen G1–G20 aggregate closure is
unchanged: per-operator generation is a separate, flag-gated mode.

Development now moves to the **SonicBoom** runtime architecture
(C++ → runtime → C ABI).

## Frozen baseline

SonicCross targets one pinned PyTorch revision and does not track upstream:

- repository: `pytorch/pytorch`
- branch: `release/2.14`
- commit: `41ffbc4a994e058af9fe00ed5caba73fc1033359`
- version: `2.14.1a0`

## Architecture

```
native_functions.yaml ─┐
tags.yaml ─────────────┼─► Semantic IR (SRFI-9 records) ─► emitters ─► C++ artifacts
                       ┘
```

1. **YAML ingestion** — `yaml.scm` / `yaml/ffi.scm` (libyaml-backed) parse the
   frozen inputs.
2. **Semantic IR** — `core-ir.scm`, `native-function.scm`, `schema-parser.scm`,
   `generated-functions.scm` reimplement torchgen's Python object model
   (`OperatorName`, `FunctionSchema`, `Type`, `NativeFunction`, …) as
   compiler-internal records. The IR is not a persistence or serialization
   contract.
3. **Generation closure** — one module per emitter group, e.g. `operators.scm`,
   `tensor-body.scm`, `core-sources.scm`, `backend-select.scm`, `ufunc.scm`,
   `functionalization.scm`. Each renderer is byte-compared against frozen
   torchgen.

The exact generation scope (dispatch keys, sharding, file managers, and the
G1–G21 group map) is catalogued in
`design/SonicCross_Generation_Configuration_v0.md`.

## Usage

`guild torchgen` is a drop-in replacement for `python3 torchgen/gen.py`:

```sh
guild torchgen -s <source-path> -d <install-dir> [-o <depfile>] [--generate headers,sources]
```

- `-s, --source-path` — ATen source directory (default `aten/src/ATen`); reads
  `<source-path>/native/native_functions.yaml`. `tags.yaml` is **not** read at
  runtime: the frozen tag set is embedded as the `valid-tags` constant.
- `-d, --install-dir` — output root (default `build/aten/src/ATen`). Core files
  land in `<install-dir>/core/`, everything else at the top level.
- `-o, --output-dependencies` — write CMake depfiles; one per file manager
  (`<stem>.cmake`, `cpu_vec_<stem>.cmake`, `core_<stem>.cmake`,
  `cuda_<stem>.cmake`, `ops_<stem>.cmake`).
- `--generate` — subset `headers,sources` (comma-separated; `declarations_yaml`
  is accepted for CLI compatibility but is out of scope).
- `--per-operator-headers` — split operator declarations into per-operator
  headers under `ATen/ops` (the CMake per-operator build layout): `ops/{name}.h`,
  `ops/{name}_ops.h`, `ops/{name}_meta.h` (structured only),
  `ops/{name}_native.h`, and `ops/{name}_{dispatch}_dispatch.h`, with the five
  aggregate shims (`Functions.h` / `Operators.h` / `NativeMetaFunctions.h` /
  `NativeFunctions.h` / `MethodOperators.h`) reduced to include-only headers.
  The `Register{key}.cpp` sources switch to the per-operator include set too.
- `--dry-run` — render without writing files.

Out of scope (never generated by SonicCross): G21 `Declarations.yaml`,
`VmapGeneratedPlumbing.h`, AOTI `c_shim_*.cpp`, and Python bindings.

## Differential validation (developer-only)

Byte-compares SonicCross output against a frozen torchgen oracle:

```sh
SONICCROSS_PYTORCH_ROOT=/path/to/pytorch \
  tests/differential/run-differential.sh
```

The complete suite is the set of `tests/differential/run-*-differential.sh`
runners (manifest + G1–G20 + the fixture semantic dump + the per-operator
header and per-operator `Register{key}.cpp` runners); every oracle rejects a
checkout whose HEAD is not the frozen commit.

## Repository layout

- `modules/sonic-cross/` — compiler modules: YAML, IR, parser, and the G1–G20 emitters.
- `tests/` — self-contained unit tests (`make check`) and the differential harness.
- `design/` — frozen semantic documents and the generation configuration.
- `scripts/` — the `(scripts torchgen)` CLI module backing `guild torchgen`.
